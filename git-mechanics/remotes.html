🔄 Remotes

Your repo, their repo, and origin/main

Your clone is a complete, independent repository. The GitLab copy is just another repository called origin. They only talk when you run fetch, pull or push, and origin/main is your local, possibly outdated, memory of where GitLab's main was.

1 · Remote-tracking branches

origin

A nickname for a URL, created by git clone. git remote -v lists them. You can have several (origin, upstream…).

origin/main

A read-only bookmark in your repo: "last time I talked to origin, its main was here". Only fetch / pull / push update it.

Upstream

Your local main tracks origin/main. That's what lets git status say "ahead 2, behind 1", and plain git pull / git push know where to go. Set with git push -u origin feature.

Nothing is live

If a teammate pushed five minutes ago, git status still says "up to date" until you git fetch. It compares with the bookmark, not with GitLab.

2 · You + a teammate

Both repos start with C1 ← C2. Your commits are A1, A2…, your teammate's are B1, B2… (they push straight to GitLab here).

Things to try

• Commit, let your teammate push, then git push: rejected. Then compare git pull (merge commit) with git pull --rebase (linear).

• In the same situation, try git push --force: your teammate's commit vanishes from GitLab. Then try --force-with-lease instead.

3 · fetch vs pull

CommandDownloads commitsMoves origin/mainChanges your branch & files
git fetchyesyesno: always safe, inspect first with git log main..origin/main
git pullyesyesyes: fetch + merge origin/main (fast-forward or merge commit)
git pull --rebaseyesyesyes: fetch + rebase origin/main (your local commits replayed on top)
git pull --ff-onlyyesyesonly if it's a fast-forward, otherwise stops and lets you decide

Since git 2.27, a plain git pull on diverged branches asks you to choose. Set it once: git config --global pull.rebase true (linear local history) or pull.ff only (never surprise-merge).

4 · Rejected pushes & force

terminal
$ git push
To gitlab.com:team/shop.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'gitlab.com:team/shop.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. Integrate the remote changes (e.g. 'git pull ...')
hint: before pushing again.

A push is only accepted if it is a fast-forward on the remote: the remote tip must be an ancestor of what you send. Otherwise someone's commits would be dropped.

Fix: git pull --rebase (or git pull), resolve conflicts if any, then git push.

Rewrote your own branch (rebase, amend, squash)? Use git push --force-with-lease: it overwrites only if the remote is still where your origin/… bookmark says, so you can't wipe a teammate's push you haven't seen. Plain --force overwrites unconditionally.

On GitLab, main is protected: force pushes are refused there regardless.

5 · Tags

git tag -a v1.4.0 -m "Release 1.4.0"   # annotated tag on HEAD
git push origin v1.4.0                  # tags are NOT pushed by default
git push --follow-tags                   # push commits + their annotated tags
git tag -l "v1.*"                         # list
git switch --detach v1.3.2               # look at an old release

A tag is a pointer that never moves, used to mark releases. Annotated tags (-a) also store author, date and message.

On GitLab, pushing a tag can trigger a tag pipeline ($CI_COMMIT_TAG is set) that builds and deploys the release, and you can create a Release page from it. See CI/CD.

6 · Several remotes

# contributing to a project you can't push to: fork it on GitLab first
git clone git@gitlab.com:me/dbt-utils.git          # your fork = origin
git remote add upstream git@gitlab.com:org/dbt-utils.git
git fetch upstream
git rebase upstream/main          # stay current with the original
git push origin feature          # then open an MR fork → upstream

git remote -v                    # list remotes and URLs
git branch -vv                   # each branch, its upstream, ahead/behind
git fetch --all --prune          # update all, drop deleted remote branches

Remote names are only local nicknames. The convention: origin is where you push, upstream is the original project you forked from.

Inside a company, you usually don't fork: everybody pushes branches to the same GitLab project and protected branches keep main safe.
