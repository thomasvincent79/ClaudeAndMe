🦊 GitLab workflow

From issue to main, through a merge request

GitLab hosts your repository and organizes the work around it: issues describe what to do, branches hold the work, merge requests (MRs) are where code is reviewed, tested by CI and merged. Protected branches and approval rules make sure nothing reaches main any other way.

3 · Merge methods


Set per project in Settings → Merge requests. The choice shapes your main history:





  
MethodWhat GitLab doesHistoryRequires

  
Merge commit (default)Always creates a merge commit (like git merge --no-ff)Branchy, every MR visible as a mergeNothing

  
Merge commit with semi-linear historyMerge commit, but only if the branch is up to date with the targetEach MR is a "bubble" on a straight lineRebase when target moved (button in the MR)

  
Fast-forward mergeNo merge commit: main just moves to the branch tipPerfectly linearRebase when target moved

  
+ Squash commitsOption (per MR or enforced): all branch commits become oneOne commit per MRGood commit message on the MR






Common choice for data / dbt teams
  
Fast-forward or semi-linear + squash: one clean commit per MR on main, easy to read in git log and easy to revert if a model change breaks production.





4 · Protection & approvals



  
Protected branches
Settings → Repository → Protected branches: who may push (usually "No one") and who may merge (Maintainers) on main.
    Force push is disabled. Wildcards work: release/*.

  
Merge checks
Settings → Merge requests: "Pipelines must succeed", "All threads must be resolved", "Delete source branch" by default, and the merge method above.

  
Approval rules (Premium)
N approvals required, from specific groups, plus "prevent approval by author" and "remove approvals when new commits are pushed".

  
Protected tags & variables
Protected CI/CD variables (deploy credentials) are only given to pipelines on protected branches / tags, so a random branch can't read them.








.gitlab/CODEOWNERS


# owners must approve MRs touching these paths
[Data platform] @acme/data/platform
/dbt_project.yml
/macros/

[Finance models] @alice @bob
/models/marts/finance/

^[Docs]                     # ^ = optional section
*.md  @acme/data/writers






Code owners map paths to people or groups. GitLab adds them as required approvers automatically when an MR touches their files (with "Require approval from code owners" on the protected branch, Premium).


Combined with "Pipelines must succeed", this gives a clean rule: nothing reaches main without a green pipeline and the right reviewer.

Deploys to production become a manual, protected job on main or on tags. See CI/CD.



6 · Handy features






push options: create the MR from the terminal


git push -u origin 42-discount-rules \
  -o merge_request.create \
  -o merge_request.target=main \
  -o merge_request.draft \
  -o merge_request.remove_source_branch \
  -o merge_request.label="dbt"

# or with the official CLI
glab mr create --fill --draft --label dbt
glab ci status       # pipeline of the current branch






quick actions (in an MR / issue comment)


/assign @alice
/assign_reviewer @bob
/label ~dbt ~"needs review"
/milestone %"Sprint 42"
/draft          # toggle draft status
/approve
/rebase         # ask GitLab to rebase the branch
/merge          # merge when the pipeline succeeds







  
Closing keywords
Closes #42 in the MR description (or a commit message) closes the issue automatically when merged into the default branch.

  
Suggestions
Reviewers can propose an exact code change in a comment; the author applies it with one click as a commit.

  
Auto-merge
"Set to auto-merge" merges as soon as the pipeline passes and approvals are in. With merge trains (Premium), MRs are tested in the order they'll land.

  
Web IDE & Duo
Edit and commit from the browser (press . in a repo). GitLab Duo can summarize MRs, explain code and suggest fixes for failed jobs.
