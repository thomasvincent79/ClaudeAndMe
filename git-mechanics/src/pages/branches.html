🌿 Branches, merge & rebase

A branch is just a pointer

A branch is a tiny file holding one commit id. Creating one is instant, and committing simply moves it forward. HEAD says which branch you're on. Merging and rebasing are two ways to bring work back together. Type commands in the sandbox and watch the graph.

1 · Pointers & HEAD

Branch = movable label

git switch -c feature writes the current commit id into .git/refs/heads/feature. Nothing is copied. When you commit on feature, only that label moves.

HEAD = "you are here"

.git/HEAD usually contains ref: refs/heads/main. If it contains a raw SHA instead (after git switch --detach or checking out a tag), you're in detached HEAD: new commits belong to no branch.

Switching rewrites your files

git switch feature moves HEAD and updates the working directory to that branch's snapshot. git refuses if uncommitted changes would be overwritten: commit or git stash first.

Relative names

HEAD~1 = parent, HEAD~3 = great-grandparent, M1^2 = second parent of a merge, main@{yesterday} = where main was yesterday (reflog).

2 · Sandbox

Type any command below (or click one). Supported: commit, commit --amend, branch, branch -d, switch / checkout (-c / -b), merge (--no-ff), rebase, cherry-pick, reset, revert, log, reflog. Hover a commit for its full id and parents.

Things to try

• Run the 3-way merge scenario, then git reset --hard HEAD~1: the merge commit fades, main is back where it was.

• Run Rebase and compare SHAs: C3' has the same message as C3 but a different id. That's why you must not rebase what others already pulled.

• git switch C1 (detached HEAD) then git commit, then git switch main: your commit is orphaned. Rescue it with git branch rescue <sha>.

3 · Merge vs rebase

git merge featuregit rebase main (on feature)
What happensFast-forward if possible, otherwise a merge commit with two parentsYour commits are replayed one by one on top of main, as new commits
HistoryTrue history, branchy; shows when work was integratedLinear, easy to read and bisect
Rewrites commits?No: safe on shared branchesYes: new SHAs, needs push --force-with-lease if already pushed
ConflictsResolved once, in the merge commitPossibly once per replayed commit
Typical useIntegrating a finished feature into main (GitLab MR "merge")Updating your own feature branch with the latest main before review
The golden rule of rebasing

Only rebase commits that exist only on your machine or on a branch only you use. Rebasing a shared branch forces everyone else to untangle duplicated commits.

update my feature branch with main, two ways
# A · merge main into feature (no rewrite)
git switch feature
git merge main

# B · rebase feature onto main (linear)
git switch feature
git fetch origin
git rebase origin/main
git push --force-with-lease
squash merge (what GitLab can do for you)
git switch main
git merge --squash feature   # stage all changes, no commit
git commit -m "feat: discount rules (#42)"
# → one single commit on main, branch commits not kept

4 · Conflicts

A conflict happens when both sides changed the same lines of the same file (or one side deleted a file the other modified). git stops and marks the file:

app.py, during a conflict
def price(order):
<<<<<<< HEAD
    return order.total * 0.95      # your side (main)
=======
    return order.total - order.discount   # their side (feature)
>>>>>>> feature
  1. git status lists files "both modified".
  2. Edit each file: keep one side, the other, or a mix. Delete the markers.
  3. git add app.py to mark it resolved.
  4. git commit (merge) or git rebase --continue (rebase).
  5. Changed your mind? git merge --abort / git rebase --abort puts everything back.

Tip: git config --global merge.conflictstyle zdiff3 also shows the common ancestor's version between the markers, which makes intent much clearer.

5 · Interactive rebase: tidy before you push

git rebase -i HEAD~4 (the editor opens)
pick   a1d03f7 Add discount model
squash 4b9e211 fix typo           # melt into the previous commit
reword 77c2e0a add tests          # keep, but edit the message
drop   e4f1a9c debug prints       # remove entirely
# reorder lines to reorder commits

Rewrites the last N commits of your branch. Useful verbs: pick, reword, edit (stop to amend), squash / fixup (merge into previous), drop.

Workflow trick: commit fixes with git commit --fixup a1d03f7, then git rebase -i --autosquash main places and squashes them automatically.

Same golden rule as above: only on commits not yet shared, or on your own MR branch (then push --force-with-lease).

6 · Good practices

Short-lived branches

A branch that lives for days, not weeks, has small diffs and few conflicts. Merge main into it (or rebase) often.

Readable names

feature/42-discount-rules, fix/vat-rounding, chore/upgrade-dbt. GitLab can create the branch from an issue and link them.

Never commit directly to main

Protect it on GitLab (see GitLab workflow): changes arrive only through reviewed merge requests with green pipelines.

Clean up

git branch -d feature after merge, git fetch --prune to drop remote-tracking branches deleted on GitLab.
