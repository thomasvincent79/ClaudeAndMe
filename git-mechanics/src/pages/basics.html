📦 How git works

Four places your code lives

Almost every git command moves changes between four areas: the working directory (the files you edit), the staging area (what goes into the next commit), the local repository (the history in .git/) and the remote (the shared copy on GitLab). Once you see these four boxes, git status stops being cryptic.

1 · The four areas, live

You just ran git clone: the project has one commit, identical everywhere. Edit files, stage them, commit, push, and watch each change travel from left to right.

Things to try

• Edit app.py, git add it, then edit it again: the file is both staged (v2) and modified (v3). Only v2 goes into the commit.

• Create test.py and run git commit without adding it: untracked files are never committed automatically.

• Make two commits before pushing: the remote only sees them when you push, and receives both at once.

Which command moves what

Why a staging area? It lets you commit part of your work: fix a bug and refactor in the same session, then stage and commit them separately, even individual hunks with git add -p. Commits stay small and focused, which makes review, revert and bisect much easier.

2 · What is a commit?

A commit is a full snapshot of the project (not a diff), plus metadata. git stores everything as objects named by the SHA-1 hash of their content (SHA-256 repos exist but are rare), in .git/objects/:

Content-addressed

The id of an object is the hash of its content. Change one byte in a file → new blob → new tree → new commit id. That's why history can't be altered silently, and why rebase or amend always produce new SHAs.

Deduplicated

A file unchanged between 1,000 commits is stored once: every tree points to the same blob. Snapshots are cheap; git gc also packs similar blobs as deltas.

A chain of parents

Each commit points to its parent(s). History is a graph (a DAG) walked backwards from the tip. A merge commit has two parents; the first commit has none.

Branches are pointers

.git/refs/heads/main is a file containing one SHA. HEAD is a file saying which branch you're on. See the Branches page.

# peek under the hood (read-only, safe)
git cat-file -p HEAD            # the commit object: tree, parent, author, message
git cat-file -p HEAD^{tree}     # the root tree: one line per file / folder
git rev-parse HEAD main~2       # turn names into SHAs
cat .git/HEAD                    # ref: refs/heads/main

3 · Setting up

once per machine
git config --global user.name  "Thomas Vincent"
git config --global user.email "thomas@example.com"
git config --global init.defaultBranch main
git config --global pull.rebase true      # optional: pull = fetch + rebase
git config --global core.autocrlf true    # Windows: CRLF ↔ LF
git config --list --show-origin           # where each setting comes from
once per project
# start from scratch…
git init my-project && cd my-project
git remote add origin git@gitlab.com:team/my-project.git
git push -u origin main     # -u: remember origin/main as upstream

# …or copy an existing one (history included)
git clone git@gitlab.com:team/my-project.git
git clone --depth 1 <url>    # shallow: latest snapshot only (CI does this)
SSH or HTTPS?

With SSH, create a key once (ssh-keygen -t ed25519), paste the .pub file into GitLab → Preferences → SSH Keys, and never type a password again. With HTTPS, GitLab asks for a personal access token (not your password); Git Credential Manager stores it for you on Windows.

4 · Looking around

CommandWhat it answers
git status / git status -sWhich files are untracked, modified, staged? Which branch, ahead/behind the remote?
git diffWorking directory vs staging area: what you changed but did not stage yet
git diff --stagedStaging area vs last commit: exactly what git commit would record
git diff main...featureWhat the feature branch changed since it left main (what a merge request shows)
git log --oneline --graph --allThe commit graph, one line per commit, all branches
git log -p -- app.pyEvery change ever made to one file, with diffs
git log -S "discount"Commits that added or removed this string (the "pickaxe")
git show e4f1a9cOne commit: message + diff
git blame app.pyWho last changed each line, and in which commit
git bisect start / good / badBinary search through history to find the commit that introduced a bug

5 · .gitignore

.gitignore
# build outputs and caches
target/
dbt_packages/
logs/
__pycache__/
*.pyc

# secrets: never commit these
.env
profiles.yml

# ...except this one
!.env.example

Patterns listed here are invisible to git status and git add .. Commit the .gitignore itself so the whole team shares it.

It only affects untracked files. If a file is already committed, adding it to .gitignore does nothing: remove it from the index first with git rm --cached profiles.yml, then commit.

Leaked a secret? Removing it in a new commit is not enough: it's still in history. Rotate the secret first, then clean history if needed (git filter-repo). GitLab's secret detection can catch this in CI.

6 · Good commits

One idea per commit

A bug fix and a refactor are two commits. Use git add -p to split a messy working directory.

Messages that explain why

Short subject in the imperative ("Fix VAT rounding on refunds", ≤ 72 chars), blank line, then the why. Many teams use Conventional Commits: feat:, fix:, chore:…

Commit often, push when coherent

Local commits are free and private. Tidy them (squash, reword) before pushing. After pushing, they're shared history.

Never commit secrets or build outputs

.env, profiles.yml, target/, node_modules/ go in .gitignore.
