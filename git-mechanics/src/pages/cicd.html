🚀 GitLab CI/CD

Every push runs a pipeline

Put a .gitlab-ci.yml file at the root of the repo and GitLab turns each push, merge request, tag or schedule into a pipeline: jobs grouped in stages, executed by runners. CI (lint, build, test) proves a change is safe; CD (deploy) ships it to an environment.

1 · How it works

Pipeline

One run, for one commit and one trigger. Has a status (running, passed, failed, blocked, canceled) shown on the commit and the MR.

Stage

An ordered group of jobs. By default, all jobs of a stage must succeed before the next stage starts. Jobs inside a stage run in parallel.

Job

A script run in a clean environment (usually a Docker image) by a runner. Exit code 0 = success. Each job is independent: it re-clones the repo.

Runner

An agent (gitlab-runner) that picks jobs up. GitLab.com offers hosted runners; companies often add their own (group or project runners) selected with tags.

2 · Anatomy of .gitlab-ci.yml

Click any highlighted keyword to see what it does.

.gitlab-ci.yml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS
      when: never
    - if: $CI_COMMIT_BRANCH || $CI_COMMIT_TAG

stages: [lint, build, test, deploy]

default:
  image: python:3.12-slim
  interruptible: true

variables:
  PIP_CACHE_DIR: "$CI_PROJECT_DIR/.cache/pip"

lint:sql:
  stage: lint
  script:
    - pip install sqlfluff
    - sqlfluff lint models/
  allow_failure: true

build:image:
  stage: build
  image: docker:27
  services: [docker:27-dind]
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

test:unit:
  stage: test
  needs: [build:image]
  cache:
    key:
      files: [requirements.txt]
    paths: [.cache/pip]
  script:
    - pip install -r requirements.txt
    - pytest --junitxml=report.xml
  artifacts:
    when: always
    reports:
      junit: report.xml

deploy:prod:
  stage: deploy
  script: ./deploy.sh production
  environment:
    name: production
    url: https://shop.acme.com
  rules:
    - if: $CI_COMMIT_TAG
      when: manual
  resource_group: production
  tags: [deploy-runner]

Click a keyword

Every top-level key that isn't a reserved keyword (stages, workflow, default, variables, include…) is a job.

Validate before you push

In GitLab: Build → Pipeline editor validates the file, shows the merged configuration (after include) and draws the pipeline. Or run glab ci lint.

4 · rules & pipeline types

rules: first match wins
test:dbt:
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
      when: never                         # 1. not in nightly runs
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes: [models/**/*, macros/**/*]  # 2. MR touching dbt code
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
                                          # 3. always on main
    # no match → job not added to the pipeline

Each job's rules are evaluated top to bottom when the pipeline is created; the first matching rule decides (when: on_success by default, or manual, delayed, never, always). Conditions: if (variable expressions), changes (file paths), exists (file present).

only / except are the older syntax: still supported but not developed anymore, and they can't be mixed with rules in the same job.

Predefined variables

GitLab injects 100+: CI_COMMIT_SHA, CI_COMMIT_REF_SLUG, CI_PIPELINE_SOURCE, CI_DEFAULT_BRANCH, CI_PROJECT_DIR, CI_REGISTRY_IMAGE, CI_JOB_TOKEN…

Your variables

In the YAML (non-secret) or in Settings → CI/CD → Variables (secrets). Options: masked (hidden in logs), protected (only on protected branches/tags), file type (written to a temp file, path in the variable).

Precedence

Highest wins: manual run / trigger variables → project → group → instance settings → job variables: → global variables: → predefined.

Runners & tags

A job runs on any runner whose tags include all the job's tags. Use tags to target a runner with network access to your warehouse, or a GPU. Executors: docker, kubernetes, shell, instance…

Secrets

Never put credentials in .gitlab-ci.yml: it's in the repo. Use masked + protected variables, or better, short-lived credentials via OIDC (id_tokens:) with your cloud provider or Vault. Masked variables are hidden in logs but readable by any script in the job.

6 · Environments & deployments

deploy:review:
  stage: deploy
  script: ./deploy.sh review $CI_COMMIT_REF_SLUG
  environment:
    name: review/$CI_COMMIT_REF_SLUG     # one per MR branch
    url: https://$CI_COMMIT_REF_SLUG.review.acme.com
    on_stop: stop:review
    auto_stop_in: 3 days
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

stop:review:
  stage: deploy
  script: ./teardown.sh $CI_COMMIT_REF_SLUG
  environment: { name: review/$CI_COMMIT_REF_SLUG, action: stop }
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: manual

An environment records what was deployed where, and when. Operate → Environments lists them, with the commit currently deployed and a one-click rollback (re-run an older deploy job).

Review apps: one dynamic environment per MR, stopped automatically when the MR is merged or closed (on_stop).

Production: when: manual, a resource_group so two deploys never overlap, and (Premium) protected environments with deployment approvals.

Continuous delivery = every change can go to prod with one click. Continuous deployment = it goes automatically.

7 · Reuse: include, extends, components

include:
  - local: ci/dbt.yml                         # file in this repo
  - project: acme/ci-templates                # file in another project
    ref: v3.2.0
    file: /python.yml
  - template: Jobs/SAST.gitlab-ci.yml         # GitLab-provided
  - component: $CI_SERVER_FQDN/acme/components/dbt-ci@1.4.0
    inputs:
      dbt_version: "1.8.6"

.python:                 # hidden job (starts with a dot)
  image: python:3.12-slim
  before_script: [pip install -r requirements.txt]

test:unit:
  extends: .python          # deep-merge the hidden job
  script: pytest

include splits or shares configuration. Templates from a central project keep 50 repos consistent.

extends (or YAML anchors, or !reference [.python, before_script]) avoids copy-pasting job settings.

CI/CD components are versioned, reusable pipeline units with typed inputs, published in the CI/CD Catalog. Pin a version (@1.4.0) rather than @main.

8 · Example: dbt slim CI

A complete pipeline for a dbt Core project (dbt 1.8.6, works the same on 1.12). In an MR, it only builds modified models and their children in a throw-away schema, deferring the rest to production. On main, it deploys to prod and saves the manifest that the next MR will compare against. (Background on --defer / state:modified: see the dbt mechanics site.)

.gitlab-ci.yml
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_PIPELINE_SOURCE == "schedule"

stages: [lint, ci, deploy]

default:
  image: python:3.11-slim
  interruptible: true
  before_script:
    - pip install dbt-core==1.8.6 dbt-snowflake~=1.8.0 sqlfluff-templater-dbt awscli
    - dbt deps
  cache:
    key: { files: [packages.yml] }
    paths: [dbt_packages/]

variables:
  DBT_PROFILES_DIR: "$CI_PROJECT_DIR/ci"    # ci/profiles.yml reads env_var('SNOWFLAKE_PASSWORD') etc.
  DBT_CI_SCHEMA: "ci_mr_${CI_MERGE_REQUEST_IID}"

lint:sqlfluff:
  stage: lint
  script: sqlfluff lint models/
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      changes: [models/**/*.sql]

dbt:slim-ci:
  stage: ci
  script:
    - aws s3 cp s3://acme-dbt-state/prod/manifest.json prod-state/manifest.json
    - dbt build --select state:modified+ --defer --state prod-state --target ci
  artifacts:
    when: always
    paths: [target/run_results.json, target/manifest.json]
    expire_in: 1 week
  environment:
    name: ci/mr-$CI_MERGE_REQUEST_IID
    on_stop: dbt:drop-ci-schema              # cleaned when the MR closes
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

dbt:drop-ci-schema:
  stage: ci
  script: dbt run-operation drop_schema --args "{schema: $DBT_CI_SCHEMA}" --target ci   # your own small macro
  environment: { name: ci/mr-$CI_MERGE_REQUEST_IID, action: stop }
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
      when: manual
  allow_failure: true

dbt:prod:
  stage: deploy
  script:
    - dbt build --target prod
    - aws s3 cp target/manifest.json s3://acme-dbt-state/prod/manifest.json
  environment: { name: production }
  resource_group: dbt-prod
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH   # every merge to main
    - if: $CI_PIPELINE_SOURCE == "schedule"          # + nightly run

Why a per-MR schema?

Two MRs in flight would otherwise overwrite each other's tables. ci/profiles.yml sets schema: "{{ env_var('DBT_CI_SCHEMA') }}" for the ci target.

Where does the prod manifest live?

Here in object storage, written by the prod job. Alternatives: the generic package registry, or needs: project: to fetch another pipeline's artifacts (Premium).

Make it a required check

Turn on "Pipelines must succeed": an MR that breaks a model or a test can't be merged into main.

9 · Best practices & debugging

Fast feedback first

Cheap checks (lint, unit tests) early; slow ones later or in parallel with needs. Aim for an MR pipeline under ~10 minutes.

Avoid duplicates & waste

Use workflow:rules (branch or MR pipeline), interruptible: true + "auto-cancel redundant pipelines", and rules:changes for path-specific jobs.

Reproducible jobs

Pin image tags and tool versions (python:3.11-slim, dbt-core==1.8.6). Pin include refs and component versions.

Protect deploys

Prod jobs: protected variables, protected environment, resource_group, manual or tag-only. Never let an MR from any branch reach prod credentials.

Debug a red job

Read the log from the bottom. Re-run with variable CI_DEBUG_TRACE: "true" (prints every command, can reveal secrets: use sparingly). Run pipeline lets you pass variables by hand.

"Works locally, fails in CI"

CI starts from a clean clone: missing files that are in .gitignore, env vars only set on your laptop, a different tool version, or a shallow clone (GIT_DEPTH) without the history a command needs.
