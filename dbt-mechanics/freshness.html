⏱️ Source freshness

Is the raw data late?

Freshness checks answer one question before you build anything: when did data last land in this source? dbt computes age = now − max(loaded_at) and compares it with warn_after / error_after. The idea is the same in 1.8.6 and 1.12. Where the YAML keys go has changed.

1 · How it's computed 2 · Freshness simulator 3 · Configuration by version 4 · Build only what got fresher 5 · Best practices

1 · How it's computed

It runs only with dbt source freshness. dbt build and dbt run do not check freshness, so schedule it as the first step of the job. Results go to target/sources.json. A source without any freshness config (or with freshness: null) is skipped.

3 · Configuration by version

1.8.6

freshness and loaded_at_field are properties of the source or table (top-level keys).

models/staging/shop/_sources.yml
sources:
  - name: shop
    database: raw
    loaded_at_field: _etl_loaded_at
    freshness:                       # default for every table
      warn_after: {count: 12, period: hour}
      error_after: {count: 24, period: hour}
    tables:
      - name: orders
        freshness:                     # stricter override
          warn_after: {count: 6, period: hour}
          error_after: {count: 12, period: hour}
          filter: _etl_loaded_at >= dateadd('day', -3, current_timestamp)
      - name: customers
      - name: payments
      - name: product_skus
        freshness: null                # opt out

Without loaded_at_field, adapters that support it (Snowflake, BigQuery, Redshift, Databricks, since 1.7) fall back to warehouse metadata. On Postgres you must provide the field.

1.12

freshness moved under config: (1.9) and so did loaded_at_field (1.10). The old placement still works but warns (1.10+ deprecations). New in 1.10: loaded_at_query for custom logic.

models/staging/shop/_sources.yml
sources:
  - name: shop
    database: raw
    config:
      loaded_at_field: _etl_loaded_at
      freshness:
        warn_after: {count: 12, period: hour}
        error_after: {count: 24, period: hour}
    tables:
      - name: orders
        config:
          freshness:
            warn_after: {count: 6, period: hour}
            error_after: {count: 12, period: hour}
            filter: _etl_loaded_at >= dateadd('day', -3, current_timestamp)
      - name: events
        loaded_at_query: |                # 1.10+, not combinable with loaded_at_field
          select max(_loaded_at) from {{ this }}
          where _loaded_at > dateadd(day, -7, current_date)
          qualify count(*) over (partition by _loaded_at::date) > 2000
      - name: product_skus
        config:
          freshness: null

Project-wide default: sources: +freshness: … in dbt_project.yml. On BigQuery, wildcard tables (events_*) get unreliable metadata freshness. Enable bigquery_reject_wildcard_metadata_source_freshness (1.12) to make that an error, and use a field instead.

4 · Build only what got fresher

Run freshness twice and compare. source_status:fresher+ selects the sources whose max_loaded_at moved since the previous run (the sources.json in --state), plus everything downstream. This works in both versions. Click the sources to change which ones received data.

$dbt source freshness  # writes target/sources.json
$dbt build -s "source_status:fresher+" --state previous-run-artifacts/
Typical use

A job that runs every 15 minutes but only rebuilds the parts of the DAG with new data. Keep the previous run's sources.json (and manifest.json) as the state for the next run.

5 · Best practices

Set thresholds from the SLA

  • warn_after ≈ the normal load interval plus a margin, and error_after = when consumers are actually hurt.
  • Set defaults at the source level (or in dbt_project.yml) and override per table.
  • Opt out static tables (freshness: null) instead of loosening the thresholds.

Make the query cheap and honest

  • The loaded-at column should be the load timestamp (ETL), not the business event time, which can be legitimately old.
  • Add a filter on big tables so the max() scans a few partitions only.
  • Use timestamps in UTC (or cast them). dbt compares against UTC now.

Wire it into orchestration

  • Run dbt source freshness first. An ERROR (exit 1) stops the pipeline before you publish stale marts.
  • If you'd rather build anyway and alert, run it as a separate, non-blocking step.
  • Use source_status:fresher+ for frequent, cheap incremental jobs.
  • In 1.8.6, -o / --output changes where sources.json is written.In 1.12, -o / --output is deprecated (1.10). Use --target-path.

Note: model-level freshness: build_after configs you may see in the docs belong to dbt platform (state-aware orchestration). They aren't used by dbt Core runs.
