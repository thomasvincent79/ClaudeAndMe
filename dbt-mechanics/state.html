🧭 State

Compare with a previous run, build only what matters

"State" means the artifacts of another run (usually production): manifest.json, run_results.json and sources.json. You give them to dbt with --state. dbt can then select what changed (state:), what failed (result:), or what got new data (source_status:), read unbuilt parents from prod (--defer), or clone prod (dbt clone). It's the engine behind slim CI, cheap retries and fast dev loops, in 1.8.6 and 1.12.

1 · The artifacts that make up "state"

1.8.6 
# after every prod run: save the artifacts outside target/
aws s3 sync target/ s3://acme-dbt-artifacts/prod/ \
  --exclude "*" --include "manifest.json" --include "run_results.json" --include "sources.json"

# anywhere else (CI, dev):
aws s3 sync s3://acme-dbt-artifacts/prod/ prod-artifacts/
dbt build -s state:modified+ --defer --state prod-artifacts/
# or: export DBT_STATE=prod-artifacts/   DBT_DEFER=true
1.12 
# same workflow; env vars use the 1.11+ prefix
export DBT_ENGINE_STATE=prod-artifacts/
export DBT_ENGINE_DEFER=true
dbt build -s state:modified+
# combine with named selectors (1.12):
dbt build -s "selector:tickets,state:modified+"

On the dbt platform, the artifacts are stored for you and CI jobs defer automatically. dbt State keeps model-level state without a manifest file (see the dbt Cloud page).

5 · Retry with result: (run_results.json)

Last night, fct_orders errored, so its children were skipped. Use the previous run_results.json as state to re-run only what's needed:

-s

dbt retry (1.6+) is the simplest: it reads target/run_results.json and re-runs from the failure point with the same command and flags. result: selectors give you more control (for example 1+result:fail rebuilds the models whose tests failed).

6 · How to leverage state: 6 recipes

🧪

Slim CI

dbt build -s state:modified+ --defer --state prod/

Build and test only what the PR changed, plus its children. Read every other parent from prod. Minutes instead of hours.

💻

Dev without rebuilding upstream

dbt run -s my_model --defer --state prod/ --favor-state

--favor-state reads prod even if a stale copy exists in your dev schema.

🚀

Deploy only what changed

# merge job on main
dbt build -s state:modified+ --state last-prod/

After a merge, rebuild just the changed models and their children instead of the whole project, then upload the new manifest.

🔁

Retry a failed night

dbt retry
# or explicit:
dbt build -s "result:error+ result:skipped+" --state target_last/
⏱️

Build only what got data

dbt source freshness
dbt build -s source_status:fresher+ --state last-run/

For frequent jobs: unchanged branches of the DAG are skipped.

🧬

Warm CI for incrementals

dbt clone -s "state:modified+,config.materialized:incremental" --state prod/
dbt build -s state:modified+ --defer --state prod/

Incremental models start from a zero-copy clone of prod (Snowflake, BigQuery, Databricks).

7 · Pitfalls

1.8.6
  • Env-aware configs = false positives: anything rendered from target.name / env_var differs between CI and prod, so whole folders look modified. Workarounds: put environment-specific naming in generate_schema_name / generate_alias_name (relation changes are compared regardless of target), keep other configs environment-independent, or accept the extra builds.
  • state:old / state:unmodified don't exist yet. Use --exclude state:modified.
1.12
  • Unrendered config comparison is on by default (flag matured in 1.12), which removes most env-aware false positives. Regenerate the state with 1.9+, otherwise you still get them.
  • New state:old, state:unmodified (1.9). Env vars DBT_ENGINE_STATE / DBT_ENGINE_DEFER.
  • Never point --state at target/: dbt overwrites target/manifest.json while parsing. Copy the artifacts to their own folder.
  • Stale state = wrong diff: always use the manifest of the latest prod run, and upload it after every prod and merge job.
  • Vars and env vars aren't tracked: changing a var's value alone doesn't mark models modified.
  • Seeds over 1 MiB are compared by path only, so content edits go unnoticed.
  • Cross-environment tests: with --defer, a relationships test can compare CI data with prod data. Exclude it in CI if it's noisy (--exclude test_name:relationships).
  • Don't use state:modified in scheduled prod jobs: when nothing changed in the code, it builds nothing.
