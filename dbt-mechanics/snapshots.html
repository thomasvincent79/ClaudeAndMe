Snapshots & hard deletes

A snapshot turns a mutable source table into a type 2 slowly changing dimension: every time a row changes, the old version is closed and a new version is inserted. The tricky part is rows that disappear from the source. That is what invalidate_hard_deletes (1.8.6) and hard_deletes (1.9+, so 1.12) control.

1 · How a snapshot run works

On every dbt snapshot, dbt compares the result of your select with the current rows of the snapshot table (the rows where dbt_valid_to is null), matched on unique_key. Then it merges three (or four) kinds of changes:

Meta columnMeaning
dbt_scd_idHash that identifies one version of a row (unique per row of the snapshot).
dbt_updated_atThe updated_at value of the source row (timestamp strategy), or the snapshot time (check strategy and delete markers).
dbt_valid_from / dbt_valid_toValidity window. dbt_valid_to is null means "current version". In 1.12 you can set dbt_valid_to_current: "to_date('9999-12-31')" to get a far-future date instead of null.
dbt_is_deleted 1.9+Only with hard_deletes: new_record. The strings 'True' (deletion marker) or 'False'.

2 · Configuration

1.8.6

Snapshots are defined only in SQL, inside a {% snapshot %} block. target_schema is required, and generate_schema_name is not applied (the same schema in dev and prod unless you use Jinja).

snapshots/orders_snapshot.sql
{% snapshot orders_snapshot %}
{{
  config(
    target_schema='snapshots',
    unique_key='id',
    strategy='timestamp',
    updated_at='updated_at',
    invalidate_hard_deletes=True
  )
}}
select * from {{ source('shop', 'orders') }}
{% endsnapshot %}
1.12

Snapshots can be defined in YAML (recommended, since 1.9). The legacy SQL block still works. schema/database are optional and follow generate_schema_name like models do. invalidate_hard_deletes still works for existing snapshots, but cannot be combined with hard_deletes.

snapshots/orders_snapshot.yml
snapshots:
  - name: orders_snapshot
    relation: source('shop', 'orders')
    config:
      unique_key: id
      strategy: timestamp
      updated_at: updated_at
      hard_deletes: new_record   # ignore | invalidate | new_record
      dbt_valid_to_current: "to_date('9999-12-31')"  # optional
      snapshot_meta_column_names:            # optional renames
        dbt_valid_from: valid_from
        dbt_valid_to: valid_to

If you need transformation logic, put it in an ephemeral model and use relation: ref('stg_orders_for_snapshot').

3 · timestamp vs check

strategy: timestamp

A row has changed if source.updated_at > current.dbt_valid_from.

Use when the source has a reliable updated_at that changes on every update. It is cheap (one column compared) and gives accurate validity windows (they come from the source, not from the run time).

strategy: check

A row has changed if any column in check_cols differs ('all' = every column). Validity windows use the run time.

Use when there is no trustworthy updated_at. Prefer an explicit column list (or a hash column) over 'all' on wide tables. A change made and then reverted between two runs is invisible.

Hard deletes work with both strategies

Deletion detection happens on unique_key only, whatever the strategy. The closing time of a deleted row is always the snapshot run time (snapshot_get_time()), because the source no longer tells you when the row disappeared.

1.8.6

Find deleted orders: there is no flag, so you infer it. An order is deleted when it has no current row:

select id, max(dbt_valid_to) as deleted_at
from {{ ref('orders_snapshot') }}
group by id
having count(case when dbt_valid_to is null then 1 end) = 0

This cannot tell you how many times an order was deleted and restored without comparing consecutive windows (looking for gaps).

1.12

Find deleted orders with new_record: the marker row says it directly.

select id, dbt_valid_from as deleted_at
from {{ ref('orders_snapshot') }}
where dbt_is_deleted = 'True'
  and dbt_valid_to is null      -- still deleted today

Drop the last line to list every deletion event, including orders that came back later.

6 · Best practices: when to use which

Use ignore when…

  • the source never hard-deletes (soft deletes via a status column), or
  • the snapshot selects a subset of the source (a where clause, incremental extract) where "missing" doesn't mean "deleted".

Use invalidate when…

  • you are on 1.8.6 and the source hard-deletes rows (it is your only option),
  • consumers only need "current rows" and as-of queries, not "when/how often was it deleted".

Use new_record when…

  • deletions are business events (churned customer, cancelled contract) you need to report on,
  • you need continuous history with no gaps, and rows can come back.
  • Start it on a new snapshot: dbt does not migrate an existing table to it automatically.
The #1 hard-delete trap: the select must return the FULL source

Detection works by "key is missing from the select". If your snapshot query filters (where updated_at > current_date - 7, a partial extract, a source that only lands deltas), every row outside the filter looks deleted and gets invalidated on every run. Hard-delete detection requires a complete extract each time.

  • Test the unique_key: add unique + not_null tests on the source column. Duplicate keys corrupt the snapshot (several current rows per key).
  • Snapshot sources, not marts: keep the select close to raw data (light renames and casts only). Logic changes later would otherwise rewrite history.
  • Run frequency = granularity: changes that happen and get reverted between two runs are lost. Snapshot at least as often as you need history.
  • Timestamps: with invalidate/new_record, dbt_valid_to mixes source updated_at values and the warehouse's current_timestamp. Keep both in the same type and timezone (1.9+ warns when the data types differ).
  • Never full-refresh a snapshot: the history only exists in that table. Back it up before changing its config.
  • Migrating 1.8 → 1.12: invalidate_hard_deletes=true → hard_deletes: invalidate is a drop-in rename. Moving to new_record adds the dbt_is_deleted column, and past deletions won't have markers, so plan a migration or start fresh.
