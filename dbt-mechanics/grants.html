🔐 Grants

Who can read what dbt builds, declared in code

The grants config (since 1.2, so identical in 1.8.6 and 1.12) declares who gets which privilege on the tables and views dbt builds. After each build, dbt makes the object's grants match the config exactly: it grants what's missing and revokes what isn't listed. The idea is the same everywhere; privilege names, grantee formats and what you still have to manage yourself differ by platform.

1 · What the grants config manages

✓ Manages

  • Privileges on the objects dbt builds: models, seeds, snapshots.
  • Only on nodes that have a grants config. No config means dbt doesn't touch the grants.
  • The listed privileges: select on most platforms, IAM roles on BigQuery.

✗ Doesn't manage

  • Database / schema / catalog access (USAGE, USE SCHEMA).
  • Future grants, ownership, warehouses, masking / row-access policies.
  • Sources: dbt doesn't build them, so it doesn't grant on them.

⚠ Consequence

On a node with grants config, dbt owns those privileges: a select granted by hand in the console is revoked at the next run. Every grant you want must be in code.

2 · Inheritance and the + prefix

dbt_project.yml: grants by layer and environment 
models:
  my_project:
    staging:
      +grants:
        select: []                       # private: nobody but the owner
    marts:
      +grants:                           # the leading + is mandatory here
        select: "{{ ['reporter', 'bi_role'] if target.name == 'prod' else ['dev_reader'] }}"
seeds:
  my_project:
    +grants:
      select: ['reporter']
snapshots:
  my_project:
    +grants:
      select: ['auditor']
model level: override vs add 
-- replaces the folder's list → only data_science
{{ config(grants = {'select': ['data_science']}) }}

-- '+select' ADDS → reporter, bi_role, data_science
{{ config(grants = {'+select': ['data_science']}) }}

-- revoke everyone on this model
{{ config(grants = {'select': []}) }}

Two different + signs: +grants in dbt_project.yml marks a config key, and '+select' inside grants means "append to the inherited grantees". Each privilege decides separately.

Snowflake: copy_grants 
models:
  my_project:
    marts:
      +copy_grants: true    # keep privileges across CREATE OR REPLACE
      +grants:
        select: ['REPORTER']

false (default): the replaced object starts clean and dbt grants again, so readers can lose access for a short moment. true: old privileges carry over and dbt revokes the extras. dbt-snowflake 1.13+ adds IGNORE GRANTS when copy_grants is false.

BigQuery: grants + authorized views 
models:
  - name: rpt_revenue
    config:
      grants:
        roles/bigquery.dataViewer:
          - group:finance@acme.com
          - serviceAccount:looker@acme.iam.gserviceaccount.com
      grant_access_to:              # authorize this VIEW on another dataset
        - project: acme-prod
          dataset: raw_finance

5 · What grants don't cover, and how to fill the gaps

Schema access with on-run-end (both versions) 
# dbt_project.yml (Snowflake / Postgres / Redshift syntax)
on-run-end:
  - "{% for schema in schemas %}grant usage on schema {{ schema }} to role reporter;{% endfor %}"
# 'schemas' = every schema this run built into

On Databricks use grant use schema on schema … to `analysts`. Prefer a macro for anything longer than one line.

Or outside dbt
  • Infrastructure as code (Terraform, Pulumi, permifrost for Snowflake): databases, schemas, roles, warehouses, future grants.
  • Snowflake future grants (grant select on future tables in schema … to role …): new objects get the privilege automatically. They work with dbt as long as the dbt grants config lists the same roles, or you don't use a grants config on those models.
  • Masking / row-access policies: post-hooks, or Snowflake tag-based policies. 1.12: Databricks row_filter config.
1.8.6

Grants config as described here. Env vars like DBT_TARGET drive the target.name conditionals.

1.12

The same grants config and semantics. Around it: stricter YAML validation (a typo like +grant: now warns), Snowflake copy_grants also on dynamic tables (1.11), Databricks row_filter (1.12), and UDFs as dbt resources (1.11) whose access you manage like other objects.

6 · Best practices

  • Grant to roles or groups, never to individual users. People change, roles don't.
  • Set grants per folder in dbt_project.yml: staging private, marts readable by BI. Use model-level config for exceptions, and '+select' to add rather than replace.
  • Make them environment-aware with target.name: prod grants to BI, dev grants to nobody (or a dev reader).
  • Let dbt own select on what it builds. Don't grant by hand on those objects, because it will be revoked. Everything else (schemas, roles, warehouses) belongs to IaC or to a run hook.
  • Check in the logs: dbt --debug run -s fct_orders shows every show grants / grant / revoke statement.
  • Avoid access gaps on Snowflake tables that are read constantly: copy_grants: true keeps access during a CREATE OR REPLACE.
