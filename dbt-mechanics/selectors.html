🎯 Node selection

Selectors, step by step

Every dbt build / run / test / ls starts by turning your -s / --exclude / --selector into a set of nodes. This page animates that evaluation on a small "tickets" project, then shows how to organise selectors on 3 levels (job → subjobs → tags) to orchestrate execution, in 1.8.6 and 1.12.

1 · How a selection is evaluated

Two consequences people miss

• Selection decides what runs, never in which order. dbt always executes the selected nodes in DAG order, in parallel waves limited by threads.

• Nodes that aren't selected are not built, but their relations are still read by ref(). They must exist in the target (or use --defer).

Precedence trap

tag:hourly,path:models/tickets/marts tag:sla means (hourly ∩ marts) ∪ sla. Commas bind tighter than spaces, and there are no parentheses on the CLI. For more complex logic, use selectors.yml.

5 · selectors.yml

A versioned file at the project root that gives names to selections. You can use full logic (union / intersection / exclude, graph options, a per-criterion indirect_selection) and reuse one selector inside another with method: selector.

1.8.6
selectors.yml
selectors:
  - name: tickets_hourly
    description: "hourly models of the tickets domain"
    definition:
      intersection:
        - method: path
          value: models/tickets
        - method: tag
          value: hourly
          parents: false          # graph options as keys:
          children: false         # parents, children, *_depth,
                                  # childrens_parents (= @)
  - name: tickets_hourly_no_sla
    definition:
      intersection:
        - method: selector        # reuse!
          value: tickets_hourly
        - exclude:
            - method: tag
              value: sla
dbt build --selector tickets_hourly
dbt ls --selector tickets_hourly_no_sla      # check before running
# ✗ in 1.8 you cannot mix: --selector X -s tag:sla (the -s is ignored)
1.12

Same file and syntax. New: the selector: method works in -s / --exclude, so named selectors compose with anything.

dbt build -s "selector:tickets_hourly"
dbt build -s "selector:tickets_hourly state:modified+"   # union
dbt build -s "selector:tickets_hourly,state:modified+"   # intersection
dbt build -s "selector:tickets" --exclude "selector:tickets_hourly"
# --selector + -s together now raises SelectExcludeIgnoredWithSelectorWarning

default: true on one selector applies when a command has no selection. Since 1.12 it is replaced, not combined, when you pass -s (use -s "selector:my_default tag:x" to combine them).

6 · A 3-level hierarchy: job → subjobs → tags

Goal: one main job tickets (L1), split into subjobs per layer (L2: staging, intermediate, marts), each split into children by tag (L3: hourly, daily, weekly). Two building blocks: folders + cumulative tags in dbt_project.yml, and one named selector per node of the tree, each level reusing its parent.

dbt_project.yml (both versions) 
models:
  my_project:
    tickets:
      +tags: [tickets]            # L1, inherited by everything below
      staging:
        +tags: [staging]          # L2 (path works too)
      intermediate:
        +tags: [intermediate]
      marts:
        +tags: [marts]
# L3 (cadence) is set per model:
# {{ config(tags=['hourly']) }}  or in the model's YAML
generate selectors.yml with Python (keeps the 3 levels in sync) 
import yaml
TREE = {"staging": ["hourly", "daily"],
        "intermediate": ["hourly"],
        "marts": ["hourly", "daily", "weekly"]}
sel = [{"name": "tickets",
        "definition": {"method": "path", "value": "models/tickets"}}]
for layer, tags in TREE.items():
    l2 = f"tickets__{layer}"
    sel.append({"name": l2, "definition": {"intersection": [
        {"method": "selector", "value": "tickets"},
        {"method": "path", "value": f"models/tickets/{layer}"}]}})
    for tag in tags:
        sel.append({"name": f"{l2}__{tag}", "definition": {"intersection": [
            {"method": "selector", "value": l2},
            {"method": "tag", "value": tag}]}})
yaml.safe_dump({"selectors": sel}, open("selectors.yml", "w"), sort_keys=False)

7 · Running the levels: 3 strategies

Orchestrate
indirect_selection in leaves
modeltestdbt startup / parse

A · One invocation for L1

dbt build --selector tickets

dbt orders everything and fills the threads. It's the fastest, and every test runs once after its parents. The levels then serve reruns and backfills (--selector tickets__marts__daily), not the normal run.

B · One invocation per subjob (L2)

staging → intermediate → marts

Good when the orchestrator must show or retry layers separately (SLA per layer, different warehouses). Costs one parse per subjob, and parallelism across layers is lost.

C · One invocation per leaf (L3)

marts/hourly ∥ marts/daily ∥ marts/weekly

Maximum control, but more overhead. Tests that span leaves (like rel_fct_tickets_agent) run twice with eager, and can run before the other parent is rebuilt. Use indirect_selection: cautious in the leaves, plus a final cross-leaf test step.

Airflow: TaskGroups mirror the levels (works with 1.8.6 and 1.12) 
from airflow.utils.task_group import TaskGroup
from airflow.operators.bash import BashOperator

TREE = {"staging": ["hourly", "daily"], "intermediate": ["hourly"],
        "marts": ["hourly", "daily", "weekly"]}

with DAG("tickets", schedule="0 * * * *", catchup=False) as dag:      # L1
    prev = None
    for layer, tags in TREE.items():
        with TaskGroup(layer) as tg:                                    # L2
            for tag in tags:                                            # L3, in parallel
                BashOperator(task_id=tag,
                    bash_command=f"dbt build --selector tickets__{layer}__{tag}")
        if prev: prev >> tg
        prev = tg
    prev >> BashOperator(task_id="cross_leaf_tests",
                         bash_command="dbt test --selector tickets")
dbt Cloud / platform

A job has ordered steps, so L2 maps naturally to commands in one job:

Job "tickets"   (schedule: hourly)
  1. dbt build --selector tickets__staging
  2. dbt build --selector tickets__intermediate
  3. dbt build --selector tickets__marts

For L3, either more steps, or separate jobs chained with Run on completion. On the platform v1 Latest / 1.12 you can write -s "selector:tickets__marts tag:sla".

Recommended design

• Let dbt handle ordering inside a run (strategy A or B). Use the orchestrator for schedules, retries and alerting.

• Tags are usually best as the schedule dimension: an hourly job intersection: [selector: tickets, tag: hourly] keeps DAG order across layers in one invocation. A daily job then runs tag:daily plus whatever it needs (+tag:daily or @).

• Before shipping a selector, check it with dbt ls --selector X --resource-type model. Add a CI check that every model belongs to exactly one L3 leaf, so no model is orphaned or run twice.
