🧬 dbt clone

Copy prod into your schema without copying data

dbt clone (available since 1.6, so in both 1.8.6 and 1.12) reads another environment's manifest.json (--state) and recreates the selected relations in your target. Where the warehouse supports it, that's a zero-copy clone. Elsewhere it's a pointer view. No model SQL is executed.

1 · How it works 2 · Clone simulator 3 · clone vs --defer 4 · Usage & versions 5 · When to use it

1 · How it works

Clone statements are independent of each other, so raise --threads (for example 32 or 50) to clone a whole project in seconds. Models, seeds and snapshots are all cloned as relations. Tests are not.

3 · clone vs --defer

What it doesAt compile time, ref() to an unbuilt model points to the prod relationCreates real objects in your schema (clones or views)
Warehouse objects createdNoneOne per selected node
CostFreeMetadata ops (zero-copy) or views; small
Visible outside dbt (BI tool, notebooks)?No: your schema stays partialYes: the schema is complete
Incremental model starts "warm"No: the first build in your schema is a full buildYes on zero-copy warehouses (the clone is a table)

Rule of thumb

Use --defer by default. Reach for clone when something outside dbt must see a complete schema, or when you need incremental models to start from prod's data.

4 · Usage & versions

1.8.6 
# complete dev schema from prod
dbt clone --state prod-artifacts/ --threads 32
# CI: clone modified incremental models first, then build
dbt clone -s "state:modified+,config.materialized:incremental" --state prod-artifacts/
dbt build -s "state:modified+" --defer --state prod-artifacts/
# refresh stale clones
dbt clone --state prod-artifacts/ --full-refresh
# skip seeds (1.8 added --exclude-resource-type for clone)
dbt clone --state prod-artifacts/ --exclude-resource-type seed

Env vars: DBT_STATE, DBT_FULL_REFRESH.

1.12

Same command and behaviour. The differences come from the surrounding features:

  • Env vars use the DBT_ENGINE_ prefix (1.11): DBT_ENGINE_STATE.
  • state:modified compares unrendered configs by default (behaviour flag matured in 1.12), so fewer false "modified" nodes get cloned or built.
  • The selector: method can be used inside -s (1.12): dbt clone -s "selector:ci_incrementals".
dbt clone -s "state:modified+,config.materialized:incremental" \
  --state prod-artifacts/ --threads 32

5 · When to use it

✅ Good fits

  • CI with incremental models on Snowflake / BigQuery / Databricks: clone the modified incrementals, then build them incrementally.
  • Complete dev sandbox to explore in a BI tool or notebook.
  • Blue/green deploys: build in a staging schema cloned from prod, test, then swap.
  • Testing a BI dashboard against a change before merging.

⚠️ Watch out

  • Clones are a snapshot in time. Re-clone with --full-refresh, or they drift from prod.
  • On Postgres/Redshift you only get views, so there is no incremental benefit and a dependency on prod objects.
  • The --state manifest must match what really exists in prod (download it from the latest prod run).
  • Your target role needs read access to prod objects, plus clone privileges where applicable.

❌ Not for

  • Copying data across accounts or regions: a clone stays inside one warehouse account/project.
  • Replacing --defer in everyday dev: deferral is free and always current.
