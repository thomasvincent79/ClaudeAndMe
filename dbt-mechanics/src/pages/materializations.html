🧱 Materializations & configs

How a model becomes an object

A model is a SELECT. Its materialization decides what dbt builds from it: a view, a table, a merged incremental table, a CTE inlined downstream, or a warehouse-maintained object. Configs come from three places that combine by precise rules. Both are core certification topics, and the same in 1.8.6 and 1.12, with platform additions since.

3 · Config precedence: where configs come from and how they combine

From least to most specific: dbt_project.yml (project, then deeper folders) → properties YAML (config:) → config() in the SQL file. "More specific wins" is only true for most keys. Toggle the layers:

layers (1 = least specific)
effective config of fct_orders

Clobber (most keys)

materialized, schema, unique_key…: the most specific value replaces the others. Grants follow this rule too, unless you use the '+select' prefix (see the Grants page).

Additive

tags, pre-hook, post-hook: every level adds to the list.

Shallow merge

meta (and freshness): top-level keys merge, and a nested dict at the same key is replaced entirely.

Packages & the + prefix

Your root dbt_project.yml clobbers a package's own configs (models: dbt_utils: +enabled: false). The + prefix exists only in dbt_project.yml.

4 · Choosing a materialization

  • Start with views for staging, then switch to tables when queries get slow or the model is read often (marts, BI).
  • Go incremental only when a table build is too slow or costly. It adds complexity (filters, strategies, full refreshes).
  • Use ephemeral sparingly: it can't be queried or debugged directly. An intermediate view is usually clearer.
  • Materialized views / dynamic tables are for freshness targets the warehouse can maintain itself, within their SQL limitations.
  • Set materializations per folder in dbt_project.yml (staging: +materialized: view, marts: +materialized: table) and keep exceptions in the model.
