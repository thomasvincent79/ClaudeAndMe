Incremental strategies

An incremental model is built once in full, then on each run dbt only computes new or changed rows and folds them into the existing table. Two choices decide whether the result is correct: which rows your query selects (the is_incremental() filter) and how dbt writes them (the incremental_strategy). The simulator shows both on the same data.

1 · Anatomy of an incremental run

The first run (or --full-refresh) ignores the filter and builds the whole table. is_incremental() is true only when the table exists, the model is incremental, and it isn't a full refresh. on_schema_change (ignore by default, or fail, append_new_columns, sync_all_columns) decides what happens when the columns of the select change.

Things to try

• append: ids 3 and 5 are duplicated. append only works for immutable events.

• insert_overwrite + "updated_at > max" filter: partitions 01-01 and 01-02 are replaced by only the changed rows, so ids 1, 2 and 4 are lost. Switch to the "event_date window" filter: now only the late row is missed.

• merge + "event_date window": the late order 8 (dated 01-01) is outside the window and is never loaded.

• microbatch: raise lookback to 3 to catch the late order. Each extra batch costs one more query.

3 · Each strategy in one sentence (plus the trap)

append

Inserts the input rows. Never updates or deletes.

Trap: re-processing a row creates a duplicate. Use it only for immutable, exactly-once data (logs, events) and keep the filter strict.

merge

MERGE on unique_key: update matches, insert the rest. Without unique_key it behaves like append.

Trap: duplicate keys in the input make the merge fail ("non-deterministic"). On huge tables it scans the whole target unless you add incremental_predicates.

delete+insert

Deletes target rows whose key is in the input, then inserts the input. Same result as merge in two statements.

Trap: it is not atomic on every warehouse. Useful when merge is unavailable (Postgres < 15) or slow, or with a coarse key like date_day to replace whole days.

insert_overwrite

Replaces entire partitions touched by the input (BigQuery, Spark, Databricks). No key matching, so it's cheap on big partitioned tables.

Trap: the select must return the complete contents of each partition it touches, or the missing rows are deleted. (On Snowflake, insert_overwrite rewrites the whole table.)

microbatch 1.9+

dbt splits the work into time batches (event_time, batch_size) and replaces each batch. You write the query for one batch, with no is_incremental().

Trap: every upstream model needs event_time or it's fully scanned for every batch. Late data older than lookback is missed.

5 · Useful options

1.8.6
models/fct_orders.sql: merge with options
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='id',                 -- or a list: ['id', 'line_no']
    merge_exclude_columns=['created_at'], -- or merge_update_columns=[...]
    incremental_predicates=[
      "DBT_INTERNAL_DEST.event_date >= dateadd(day, -7, current_date)"
    ],
    on_schema_change='append_new_columns'
) }}
select * from {{ ref('stg_orders') }}
{% if is_incremental() %}
  -- small overlap (>=, minus a margin) catches late rows; merge dedups them
  where updated_at >= (select dateadd(hour, -3, max(updated_at)) from {{ this }})
{% endif %}

A late-data backfill means a manual dbt run --full-refresh -s fct_orders, or a var-driven filter (where event_date >= '{{ var("from") }}').

1.12

Everything on the left still applies. For time-series models, microbatch adds:

models/staging/stg_orders.yml: enable upstream filtering
models:
  - name: stg_orders
    config:
      event_time: event_date
models/fct_orders.sql
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='event_date',
    batch_size='day',          -- hour | day | month | year
    begin='2024-01-01',         -- start for the first build
    lookback=3,                -- reprocess 3 previous batches
    concurrent_batches=true,    -- optional, auto-detected
    full_refresh=false          -- recommended: backfill instead
) }}
select * from {{ ref('stg_orders') }}
# targeted backfill, one query per day
dbt run -s fct_orders --event-time-start "2024-09-01" --event-time-end "2024-09-04"
# only re-run the batches that failed
dbt retry

All event times are treated as UTC. Use ref('x').render() to opt one input out of filtering (for example a small dimension).

6 · Which one to choose

Your data looks like…ChooseWhy
Immutable events, never updated, loaded exactly onceappendCheapest: no lookup in the target. Add a unique test to catch replays.
Rows updated in place, with a reliable primary key, small to medium tablemergeUpsert semantics, safe to re-run (idempotent), tolerant of overlapping filters.
Same, but very large targetmerge + incremental_predicates / clustering, or delete+insertLimits the scan of the target to recent data.
Recompute whole days at a time (aggregates by day)delete+insert with unique_key='date_day', or insert_overwriteReplaces a full slice: no per-row matching, handles deletions inside the slice.
Big partitioned table on BigQuery / Spark / Databricksinsert_overwritePartition swaps are much cheaper than MERGE. The query must return full partitions.
Big time-series fact, late data, regular backfillsmicrobatch 1.9+Batches are idempotent and retryable, backfills are a CLI flag, and the batch query is simple to read.
Big time-series fact, late data, regular backfillsinsert_overwrite / delete+insert on a date key + a lookback window in the filter 1.8.6This is what microbatch automates in 1.9+.
Rows can be hard-deleted in the sourceNone of them handles this on its ownUse a full refresh, a slice replacement (insert_overwrite/delete+insert by date), or a snapshot.
  • Make re-runs safe: prefer strategies where running the same input twice gives the same table (merge, delete+insert, insert_overwrite, microbatch).
  • Overlap your filter (>=, minus a margin) rather than using a strict >, and let the strategy deduplicate. Rows sharing the max timestamp, or late rows, are then not lost.
  • Deduplicate the input on unique_key (qualify row_number() … = 1) before a merge.
  • Test: unique + not_null on the key, and periodically compare to a full refresh (row counts and sums per day).
  • Schedule a full refresh (weekly or monthly) if the model can drift. With microbatch, prefer a backfill over the period instead.
