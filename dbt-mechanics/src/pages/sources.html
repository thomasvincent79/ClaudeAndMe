🔌 External dependencies

Sources in, exposures out, packages around

Your project sits between sources (raw tables loaded by someone else) and exposures (the dashboards, ML models and apps that read your marts). Packages bring code from other projects. Declaring all three makes lineage complete end to end, and lets you select by business impact. The same in 1.8.6 and 1.12, with YAML moves and private packages in 1.12.

1 · Sources

1.8.6
models/staging/stripe/_stripe__sources.yml
sources:
  - name: stripe                    # source('stripe', …)
    database: raw
    schema: stripe_prod             # default: the source name
    loader: fivetran
    loaded_at_field: _fivetran_synced
    freshness:
      warn_after: {count: 6, period: hour}
    tables:
      - name: payments
        identifier: PAYMENTS_V2     # real table name, if different
        quoting: {identifier: true}
        columns:
          - name: id
            data_tests: [unique, not_null]
1.12
models/staging/stripe/_stripe__sources.yml
sources:
  - name: stripe
    database: raw
    schema: stripe_prod
    loader: fivetran
    config:                         # freshness (1.9) and loaded_at_field (1.10)
      loaded_at_field: _fivetran_synced   # moved under config
      freshness:
        warn_after: {count: 6, period: hour}
    tables:
      - name: payments
        identifier: PAYMENTS_V2
        columns:
          - name: id
            data_tests: [unique, not_null]
select * from {{ source('stripe', 'payments') }}   -- → raw.stripe_prod."PAYMENTS_V2", plus a lineage edge
  • One source() per raw table, only in staging models. Every other model refs staging, never raw tables directly.
  • Test sources (keys, accepted values) and add freshness: problems are caught at the entrance.
  • Select them: dbt test -s source:stripe, or dbt build -s source:stripe+ for everything downstream.
  • Overriding a package's source (overrides:) warns since 1.11 (SourceOverrideDeprecation). Prefer project vars in the package, or your own source.

2 · Exposures

models/exposures.yml 
exposures:
  - name: weekly_kpis
    label: Weekly KPIs
    type: dashboard          # dashboard | notebook | analysis | ml | application
    maturity: high           # high | medium | low
    url: https://bi.acme.com/dash/42
    owner:
      name: Finance analytics
      email: fin-data@acme.com
    depends_on:
      - ref('fct_orders')
      - ref('dim_customers')
      - source('stripe', 'payments')    # sources allowed too
what you get
  • Lineage to the business: docs and Catalog show which dashboards a model feeds.
  • Selection by impact: dbt build -s +exposure:weekly_kpis rebuilds exactly what the dashboard needs.
  • Ownership: whom to warn when a model changes.
  • Exposures aren't built or run: they only declare dependencies.
  • On the dbt platform, auto-exposures import Tableau / Power BI dashboards automatically (see the dbt Cloud page).

4 · Packages

packages.yml (or dependencies.yml, 1.6+) 
packages:
  - package: dbt-labs/dbt_utils          # dbt Hub
    version: [">=1.1.0", "<2.0.0"]
  - git: "https://github.com/acme/dbt-shared.git"
    revision: v2.3.0                     # tag, branch or commit sha
    subdirectory: transform
  - local: ../shared_macros               # monorepo
  - private: acme/internal-dbt           # 1.12: native private repos over SSH
    provider: github
dbt deps                                  # install into dbt_packages/ and write package-lock.yml
dbt deps --upgrade                        # re-resolve within the ranges (1.7+)
dbt deps --add-package dbt-labs/codegen@0.13.1   # edit packages.yml for you (1.7+)

6 · Best practices

  • Ranges, not exact pins, for hub packages ([">=1.1.0", "<2.0.0"]), so packages can co-resolve. Reproducibility comes from the lock file.
  • Pin git packages to a tag or sha, never a moving branch.
  • Run dbt deps at the start of every CI and prod job (see the slim CI order on the State page).
  • Declare an exposure for every important dashboard, with an owner. Then +exposure:x becomes your "is the dashboard up to date?" job.
  • Keep source() calls in staging only, one staging model per source table.
