🏷️ Versioning

Change a model without breaking its consumers

"Versioning" in dbt means three things. Model versions let you ship a breaking change to a public model while consumers migrate at their own pace. Package and dbt-version pinning make every run reproducible. Git versions the project as a whole. Model versions exist since 1.5, so in both 1.8.6 and 1.12; 1.12 adds the latest_version_pointer.

1 · Why version a model

Non-breaking change → no version

Adding a column, adding rows, fixing a bug in values: consumers keep working. Just ship it.

Breaking change → new version

Removing or renaming a column, changing a type or nullability, changing the grain. Downstream SQL or dashboards break. Create v2 and keep v1 alive during a migration window.

Contracts make it detectable

With contract: {enforced: true}, dbt knows the declared columns and types, so it can flag a breaking change in CI (state:modified) instead of letting it reach consumers.

Things to try

• Base name = nothing, then step 3: the BI dashboard silently reads a table that nobody rebuilds anymore.

• alias on latest, steps 3 → 4: the alias moves from v1 to v2, so dim_customers changes shape at promotion. That's the moment to announce.

• latest_version_pointer: every version keeps its own _v<n> table, and dbt maintains a dim_customers view pointing to the latest.

Files and relations by default

Version v lives in dim_customers_v<v>.sql (or any file via defined_in) and builds the relation dim_customers_v<v>. The latest can also stay in dim_customers.sql. Nothing writes the bare dim_customers relation unless you decide so (alias, pointer, or a post-hook view).

4 · Configuration by version

1.8.6
models/marts/_dim_customers.yml
models:
  - name: dim_customers
    latest_version: 2
    config:
      access: public
      contract: {enforced: true}
    columns:                         # shared definition (= v1)
      - name: customer_id
        data_type: int
      - name: full_name
        data_type: varchar
      - name: country_name
        data_type: varchar
    versions:
      - v: 2
        columns:
          - include: all
            exclude: [country_name, full_name]
          - name: customer_name
            data_type: varchar
        config:
          alias: dim_customers       # latest owns the base name
      - v: 1
        deprecation_date: 2026-12-31

Alternative to the alias: keep _v1/_v2 tables and add a post-hook on the latest version, create or replace view {{ this.schema }}.dim_customers as select * from {{ this }}. Remember to move it at promotion.

1.12
models/marts/_dim_customers.yml
models:
  - name: dim_customers
    latest_version: 2
    config:
      access: public
      contract: {enforced: true}
      latest_version_pointer:       # 1.12: dbt maintains the view
        enabled: true
        # alias: dim_customers_current   (default: the base name)
    columns: [...]
    versions:
      - v: 2
        columns:
          - include: all
            exclude: [country_name, full_name]
          - name: customer_name
            data_type: varchar
      - v: 1
        deprecation_date: 2026-12-31
# or for every versioned model:
flags:
  latest_version_pointer_enabled_by_default: true

Don't combine it with alias: dim_customers on the latest version: dbt raises a name collision (dbt1005). In dbt v2 the pointer is on by default, so remove such aliases before migrating.

# selection works the same in both versions
dbt build -s dim_customers                  # all versions
dbt build -s dim_customers.v2               # one version (dim_customers_v2 also works)
dbt build -s "dim_customers,version:latest"
dbt build --exclude "version:old"           # typical default in dev, via a selectors.yml default

5 · Versioning the project itself

Pin dbt

# dbt_project.yml
require-dbt-version: [">=1.8.0", "<1.9.0"]

Fails fast if someone runs the project with another dbt. Pin adapters too (requirements.txt: dbt-snowflake==1.8.4). For 1.12: [">=1.12.0", "<1.13.0"].

Pin packages + lock

# packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.1.0", "<2.0.0"]
# dbt deps → writes package-lock.yml (commit it)
# dbt deps --upgrade → re-resolve within the ranges

The lock file (1.7+) makes installs reproducible across laptops and CI. 1.12 adds native private: packages over SSH.

Git = project version

Each prod deploy is a commit (tag releases such as v2026.11.04 if you like). The manifest of that commit is the --state for the next CI run. Model versions are for consumers, git history is for you: don't create v2 for every change.

6 · Best practices

  • Version only public, contracted models with consumers you don't control (other teams, BI, exports). Internal staging models just change.
  • Keep two live versions at most: latest and the one being deprecated. Each version is a full extra build in the warehouse.
  • Always set a deprecation_date when you promote a new latest, and announce it. Consumers see warnings on every parse until they migrate.
  • Decide the base-name strategy once and document it: alias on the latest (1.8.6)the pointer view (1.12). Without one, BI tools end up on a stale table.
  • Prerelease first: ship v2 with latest_version unchanged, let one consumer pin v=2, then promote.
  • Clean up: removing a version from YAML doesn't drop its table. Drop it yourself, or with a cleanup macro.
  • CI: run state:modified+ with contracts enforced. A breaking change without a new version is caught before merge.
