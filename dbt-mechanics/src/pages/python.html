🐍 Python models

When SQL isn't enough: Python in the DAG

A Python model is a .py file in models/ with a model(dbt, session) function that returns a DataFrame. dbt treats it like any model: refs, DAG, tests, docs. The code runs on the data platform (Snowflake, Databricks, BigQuery), never on the machine running dbt. Available since 1.3, so the same in 1.8.6 and 1.12, with a few config helpers added since.

1 · Anatomy of a Python model

models/ml/ticket_scores.py (Snowpark) 
import snowflake.snowpark.functions as F

def model(dbt, session):                     # ① fixed signature
    dbt.config(                                 # ② literals only
        materialized="table",                  #    table | incremental
        packages=["scikit-learn==1.5.*"],
    )
    tickets = dbt.ref("stg_tickets")            # ③ a DataFrame, edge in the DAG
    agents  = dbt.source("zendesk", "users")

    df = tickets.join(agents, tickets.AGENT_ID == agents.ID)
    df = df.with_column("IS_URGENT",
                        F.col("BODY").rlike("(?i)urgent|asap|down"))
    return df                                   # ④ one DataFrame → the table
models/marts/fct_ticket_kpis.sql (downstream SQL) 
select agent_id,
       avg(iff(is_urgent, 1, 0)) as urgent_rate
from {{ ref('ticket_scores') }}            -- a Python model, ref'd like any other
group by 1
  • dbt.ref() / dbt.source() return the platform's DataFrame (Snowpark, PySpark, BigFrames).
  • You may return a pandas DataFrame too. dbt converts it.
  • dbt.this (with .database, .schema, .identifier) and dbt.is_incremental are available.
  • Only table and incremental materializations. No view or ephemeral, and you can't ref an ephemeral model.
  • No Jinja: config that depends on vars, env vars or target goes through YAML (section 3).

3 · Config, vars and incremental Python models

1.8.6
models/ml/_ml.yml
models:
  - name: ticket_scores
    config:
      materialized: incremental
      unique_key: ticket_id
      # Jinja is allowed HERE, not in the .py file:
      target_name: "{{ target.name }}"
      lookback_days: "{{ var('lookback_days', 3) }}"
      meta:
        model_version: "2024-11"
def model(dbt, session):
    days = int(dbt.config.get("lookback_days"))
    mv = dbt.config.get("meta", {}).get("model_version")
    df = dbt.ref("stg_tickets")
    if dbt.is_incremental:
        df = df.filter(df.UPDATED_AT >= F.dateadd("day", F.lit(-days),
                                                  F.current_timestamp()))
    if dbt.config.get("target_name") == "dev":
        df = df.limit(1000)
    return df.with_column("MODEL_VERSION", F.lit(mv))

1.8 also lets f-strings use dbt.config.get() values (before 1.8 they rendered None).

1.12

Same pattern. Two differences:

  • Custom keys belong under meta (top-level custom config keys warn since 1.10). Read them with dbt.config.meta_get("key").
  • Microbatch (1.9+) is a SQL incremental strategy. For Python incremental models, keep the dbt.is_incremental filter.

Incremental = your filter + the adapter's strategy

dbt.is_incremental is true exactly as in SQL. You filter the new rows yourself, and dbt then merges them (unique_key) with the strategies the adapter supports for Python (for example merge on BigQuery via Dataproc).

1.12 · Python UDF as a dbt resource
functions/clean_phone.py + functions/clean_phone.yml
def clean_phone(raw: str) -> str:
    import phonenumbers
    return phonenumbers.format_number(
        phonenumbers.parse(raw, "FR"), phonenumbers.PhoneNumberFormat.E164)
functions:
  - name: clean_phone
    config:
      packages: [phonenumbers]      # 1.12
    arguments: [{name: raw, data_type: string}]
    returns: {data_type: string}
select {{ function('clean_phone') }}(phone) as phone_e164 from {{ ref('stg_users') }}
1.8.6

No functions/ resource type. Create the UDF with a macro run in on-run-start, or once by hand, and call it in SQL. Otherwise put the logic in a Python model.

6 · Limits & debugging

⚠️ Limits

  • Slower to start (procedure / cluster / session) and often more expensive than SQL.
  • dbt.config() takes literals only. Refs must be plain strings so dbt can parse the DAG.
  • Helper functions can't be imported from another model file. Use stage imports (Snowflake), a package, or a UDF.
  • Unit tests (YAML unit_tests:) target SQL models. Test your Python helpers with pytest, and the output with data tests.

🔎 Debugging

  • print() output doesn't appear in dbt logs. Look at the platform's query/job history (Snowflake query history, Spark UI, Dataproc logs).
  • dbt compile -s ticket_scores, then read the generated code in target/.
  • Iterate fast in a notebook on the same platform, or locally with dbt-duckdb, then paste the code into model().
  • In dev, return a tiny sample (if target_name == "dev": df = df.limit(1000)).

✅ Best practices

  • Keep Python models thin: SQL upstream prepares and filters, Python does the one thing SQL can't, SQL downstream aggregates.
  • Pin packages versions, so the platform environment is reproducible.
  • Stay lazy as long as possible. Call to_pandas() only on filtered, narrow data.
  • Add unique/not_null tests on the output like any model. Contracts work on Python models too.
