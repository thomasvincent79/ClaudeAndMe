🧩 Macros & Jinja

Write SQL that writes SQL

A macro is a Jinja function stored in macros/. dbt renders it while compiling, so the warehouse only ever sees plain SQL. Macros remove repetition, adapt SQL to each warehouse, override dbt's own behaviour (schema naming, materializations), and run operations (hooks, run-operation). The same in 1.8.6 and 1.12, with stricter argument validation and run-operation --sql in 1.12.

1 · Anatomy of a macro

macros/cents_to_dollars.sql 
{% macro cents_to_dollars(column_name, scale=2) %}
    round({{ column_name }} / 100.0, {{ scale }})
{% endmacro %}
models/stg_payments.sql
select
    payment_id,
    {{ cents_to_dollars('amount_cents') }} as amount
from {{ source('stripe', 'payments') }}
compiled
select payment_id, round(amount_cents / 100.0, 2) as amount from raw.stripe.payments
returning a value instead of SQL text 
{% macro get_columns_except(relation, excluded) %}
  {% set cols = adapter.get_columns_in_relation(relation) %}
  {{ return(cols | map(attribute='name')
                 | reject('in', excluded) | list) }}
{% endmacro %}
{% for c in get_columns_except(ref('stg_orders'), ['_loaded_at']) %}
  {{ c }}{% if not loop.last %},{% endif %}
{% endfor %}
  • {{ … }} prints a value, {% … %} runs logic, {# … #} is a comment.
  • {%- -%} trims whitespace around a tag, for cleaner compiled SQL.
  • Package macros are called with their namespace: {{ dbt_utils.star(ref('x')) }}.
1.8.6: document macros 
macros:
  - name: cents_to_dollars
    description: Converts cents to dollars
    arguments:
      - name: column_name
        type: string
      - name: scale
        type: integer

Used for docs only. A mismatch with the real signature isn't checked.

1.12

Same YAML. The behaviour flag validate_macro_args (introduced in 1.10, mature and on by default in 1.12) warns when documented argument names or types don't match the Jinja signature. Also new: config.meta_get() in macros (1.10) and dbt run-operation --sql (1.12).

2 · Parse vs execute: the execute flag

dbt renders Jinja twice. First at parse time, to discover refs and configs, without touching the warehouse. Then at compile/run time, for real. Any macro that queries the warehouse (run_query, statement, adapter.get_columns_in_relation…) must handle the first pass.

3 · Overriding dbt: generate_schema_name

Many dbt behaviours are macros you can replace by defining a macro with the same name in your project: generate_schema_name, generate_alias_name, generate_database_name, materializations, tests… The classic case: by default a model with +schema: marts goes into <target_schema>_marts, even in prod.

4 · adapter.dispatch: one macro, many warehouses

adapter.dispatch('name', 'namespace') picks the implementation for the current adapter: <adapter>__name, then the parent adapter's (Redshift → Postgres), then default__name. That's how packages and dbt's own cross-database macros (dbt.datediff, dbt.dateadd, dbt.concat…) work. With dispatch: in dbt_project.yml, your project can override a package's implementation.

5 · Hooks & run-operation

pre_hook / post_hook

{{ config(post_hook=[
  "alter table {{ this }} cluster by (order_date)",
  "{{ log_model_run(this) }}"
]) }}

SQL run before or after this model. Typical uses: indexes, clustering, masking policies, audit logs.

on-run-start / on-run-end

on-run-end:
  - "{{ grant_usage_on_schemas(schemas, 'reporter') }}"
  - "{{ upload_results(results) }}"

Run once per invocation. In on-run-end you get the schemas and results context variables. Since 1.12 (matured flag), a failing on-run-start skips every selected node.

dbt run-operation

dbt run-operation drop_pr_schemas --args '{"older_than_days": 7}'
dbt run-operation --sql "select count(*) from {{ ref('fct_orders') }}"   # 1.12

Calls a macro directly, outside any model: cleanup, grants, admin tasks.

7 · When (not) to write a macro

✓ Good macro

  • Logic repeated in 3+ models (unit conversions, standard cleaning).
  • Cross-database SQL (adapter.dispatch).
  • Changing dbt's behaviour (schema naming, custom materializations, generic tests).
  • Operations: grants, cleanup, auditing.

✗ Over-engineering

  • Wrapping a one-off case when: readers then have to open another file.
  • Generating whole models from config loops nobody can read in compiled/.
  • Calling run_query in many models: every compile hits the warehouse.

🔎 Debug

  • dbt compile -s model, then read target/compiled/.
  • {{ log(var, info=True) }}, and dbt --debug for the executed SQL.
  • Check dbt_packages/ for how a package macro is really implemented.
  • Test macro output with a unit test on a model that uses it.
