✅ Testing

Data tests & unit tests

dbt has eight kinds of checks, in two main families. Data tests check the data that is actually in the warehouse after a build. Unit tests (new in 1.8) check your SQL logic against small hand-written inputs before building. Both exist in 1.8.6 and 1.12; the differences are mostly in the YAML syntax and its validation.

1

Built-in generic tests

unique · not_null · accepted_values · relationships
cost ●○○

Four tests shipped with dbt. You attach them in YAML, and dbt generates the "select failing rows" query for each column.

1.8.6 
models:
  - name: fct_orders
    columns:
      - name: order_id
        data_tests: [unique, not_null]
      - name: status
        data_tests:
          - accepted_values:
              values: [placed, shipped, returned]
      - name: customer_id
        data_tests:
          - relationships:
              to: ref('dim_customers')
              field: customer_id
1.12 
models:
  - name: fct_orders
    columns:
      - name: order_id
        data_tests: [unique, not_null]
      - name: status
        data_tests:
          - accepted_values:
              arguments:
                values: [placed, shipped, returned]
      - name: customer_id
        data_tests:
          - relationships:
              arguments:
                to: ref('dim_customers')
                field: customer_id
✓ Use for the grain (primary key), mandatory columns, enums, and foreign keys. On every model, starting with sources.
✗ Not for rules involving several columns or tables (→ 2, 3 or 4), or for checking your SQL logic (→ 5).
2

Generic tests from packages

dbt_utils · dbt_expectations · elementary…
cost ●○○

The same mechanism, but written by the community. Install them with packages.yml + dbt deps, then call them by package.test_name.

models:
  - name: fct_order_lines
    data_tests:                                    # model-level test
      - dbt_utils.unique_combination_of_columns:
          arguments:                               # 1.10.5+
            combination_of_columns: [order_id, line_no]
      - dbt_utils.recency:
          arguments:
            datepart: day
            field: created_at
            interval: 1
    columns:
      - name: amount
        data_tests:
          - dbt_utils.accepted_range:
              arguments:
                min_value: 0
                inclusive: true
      - name: email
        data_tests:
          - dbt_expectations.expect_column_values_to_match_regex:
              arguments:
                regex: "^[^@]+@[^@]+$"
NeedReady-made test
composite primary keydbt_utils.unique_combination_of_columns
row-level rule across columnsdbt_utils.expression_is_true ("shipped_at >= ordered_at")
numeric boundsdbt_utils.accepted_range
data arrived recently (on a model)dbt_utils.recency
same row count as another modeldbt_utils.equal_rowcount
FK only for some rowsdbt_utils.relationships_where
regex, distributions, row-count rangesdbt_expectations.*
✓ Use as soon as a built-in test isn't enough. Check the packages before writing your own.
✗ Avoid adding a heavy package for one test (→ 3). Pin the package version.
3

Custom generic tests

your own {% test %} macro, reusable in YAML
cost ●○○

A parametrised SQL query that returns failing rows. Once written, it's used in YAML exactly like unique.

tests/generic/is_positive.sql 
{% test is_positive(model, column_name, allow_zero=false) %}
select *
from {{ model }}
where {{ column_name }} {{ '<' if allow_zero else '<=' }} 0
{% endtest %}
# model-level: no column_name argument
{% test has_rows_today(model, date_col) %}
select 1 where not exists (
  select 1 from {{ model }} where {{ date_col }} = current_date)
{% endtest %}
usage 
columns:
  - name: amount
    data_tests:
      - is_positive
  - name: discount
    data_tests:
      - is_positive:
          arguments:
            allow_zero: true
          config:
            severity: warn

Put them in tests/generic/ (or macros/). model and column_name are filled in by dbt.

✓ Use when your rule repeats across columns or models (company-specific formats, "amount positive", "no future dates").
✗ Overkill for a rule used once (→ 4).
4

Singular tests

one .sql file in tests/ = one test
cost ●●○

Write any query that returns the rows breaking a business rule. Zero rows means pass. It can join several models.

tests/assert_payments_cover_orders.sql
{{ config(severity='error', error_if='>10', warn_if='>0') }}
-- every shipped order must be fully paid
select o.order_id, o.amount, coalesce(sum(p.amount), 0) as paid
from {{ ref('fct_orders') }} o
left join {{ ref('fct_payments') }} p using (order_id)
where o.status = 'shipped'
group by 1, 2
having coalesce(sum(p.amount), 0) < o.amount

1.8.6: configure it in the file (config()) or in dbt_project.yml under data_tests:. 1.12: you can also document it in a YAML file (data_tests: - name: assert_payments_cover_orders, description: …, possible since 1.9).

✓ Use for cross-table reconciliations and one-off business rules ("revenue = sum of lines", "no order before its customer exists").
✗ Avoid copy-pasting the same singular test with another table name (→ 3).
5

Unit tests 1.8+

mocked inputs → model SQL → expected output
cost ●○○ (tiny data)

They test your code, not the data. They run before the model is built and catch logic bugs on edge cases that may not exist in prod yet.

unit_tests:
  - name: fiscal_quarter_handles_year_boundary
    model: fct_orders
    given:
      - input: ref('stg_orders')
        rows:
          - {order_id: 1, ordered_at: '2024-12-31'}
          - {order_id: 2, ordered_at: '2025-01-01'}
    expect:
      rows:
        - {order_id: 1, fiscal_quarter: 'FY24-Q4'}
        - {order_id: 2, fiscal_quarter: 'FY25-Q1'}
✓ Use for regex, case when, date math, window functions, the is_incremental() branch, and before a refactor.
✗ Not for checking real data quality (→ 1–4). Exclude them from prod runs (--exclude-resource-type unit_test).
6

Model contracts & constraints

a guarantee on the shape, checked before the build
cost ○○○

Not a test you "run", but a check: if the model's SQL doesn't produce exactly the declared columns and types, the build fails before writing the table. Constraints (not_null, primary_key, check…) go into the DDL. Only some are enforced, depending on the warehouse (Postgres enforces them all, Snowflake only not_null).

models:
  - name: dim_customers
    config:
      contract: {enforced: true}
    columns:
      - name: customer_id
        data_type: int
        constraints: [{type: not_null}, {type: primary_key}]
      - name: email
        data_type: varchar
✓ Use for public models consumed by other teams or BI. It pairs with model versions (see the Versioning page).
✗ Doesn't replace unique: most warehouses don't enforce primary_key. Keep the data test.
7

Source freshness

"did data arrive on time?"
cost ●○○

Checks max(loaded_at) against warn_after / error_after. It runs with dbt source freshness, not dbt test. See the Freshness page for the simulator.

✓ Use on every source fed by a pipeline with an SLA, as the first step of the job.
✗ Not on models: use dbt_utils.recency there (→ 2).
8

Regression / audit tests

"did my change alter results vs prod?"
cost ●●●

Compare the new version of a model with production: row counts, keys, changed values. With Core, use the audit_helper package in an analysis or a CI step. On the platform, compare changes does it automatically (see the dbt Cloud page).

{{ audit_helper.compare_relations(
     a_relation=ref('fct_orders'),                                  -- dev / CI
     b_relation=api.Relation.create(database='analytics', schema='prod', identifier='fct_orders'),
     primary_key='order_id') }}
✓ Use when refactoring a critical model: the output should be identical, or differ only where you intended.
✗ Not as a permanent scheduled test: it compares two environments.

5 · Unit tests

models/fct_orders_unit_tests.yml (same syntax in 1.8.6 and 1.12)
unit_tests:
  - name: test_amount_converted_to_eur
    model: fct_orders
    given:
      - input: ref('stg_orders')
        rows:
          - {id: 1, amount: 100, currency: 'USD'}
          - {id: 2, amount: 50,  currency: 'EUR'}
      - input: ref('stg_fx')
        rows:
          - {currency: 'USD', rate_to_eur: 0.9}
    expect:
      rows:
        - {id: 1, amount_eur: 90}
        - {id: 2, amount_eur: 50}

  - name: test_incremental_only_new_rows       # test the is_incremental() branch
    model: fct_orders
    overrides:
      macros:
        is_incremental: true
    given:
      - input: ref('stg_orders')
        rows: [{id: 1, updated_at: '2024-01-01'}, {id: 2, updated_at: '2024-01-05'}]
      - input: this                            # current state of the incremental model
        rows: [{id: 1, updated_at: '2024-01-01'}]
    expect:
      rows: [{id: 2, updated_at: '2024-01-05'}]

Unit tests also accept format: csv or sql for fixtures, fixture: files in tests/fixtures/, and overrides for vars, env_vars and macros. Run them with dbt test --select "test_type:unit" and exclude them in production with dbt build --exclude-resource-type unit_test.

6 · 1.8.6 vs 1.12 syntax

1.8.6
  • data_tests: is the new name, and tests: is still accepted (you can't use both on the same resource).
  • Test arguments sit directly under the test name (values:, to:, field:).
  • Unknown keys in YAML are silently ignored, so typos (e.g. severty: warn) go unnoticed.
  • Unit tests: new, but available in 1.8.
      - name: status
        data_tests:
          - accepted_values:
              values: ['placed', 'shipped']
              config:
                severity: warn
1.12
  • Generic-test arguments go under arguments: (1.10.5+). The old top-level form still works but raises a deprecation warning.
  • YAML is validated against a JSON schema: custom keys must move under config: meta: (warnings since 1.10, on by default for most adapters in 1.11).
  • A test config that is not a mapping raises TestConfigNotDictError (1.12).
  • Opt-in flag require_sql_header_in_test_configs allows sql_header in a generic test's config (1.12).
  • Disabling a model also disables its unit tests (1.11).
      - name: status
        data_tests:
          - accepted_values:
              arguments:
                values: ['placed', 'shipped']
              config:
                severity: warn

7 · Best practices

What to test

  • Every model's grain: unique + not_null on the primary key (or dbt_utils.unique_combination_of_columns).
  • Foreign keys with relationships, enums with accepted_values.
  • Sources: freshness plus key tests, so problems are caught at the entrance.
  • Snapshots & incrementals: key tests are mandatory (see the other pages).

Severity strategy

  • error for things that make data wrong (grain, keys).
  • warn + error_if: ">100" for "a few bad rows are tolerable".
  • where to scope a test to recent data on large tables (for example "created_at > current_date - 3").
  • store_failures: true (or --store-failures) to investigate failing rows in the _dbt_test__audit schema.

Unit test or data test?

  • Unit: complex logic you write (case/when, regex, date math, window functions, the is_incremental() branch). Test edge cases that don't exist in prod yet.
  • Data: assumptions about real data you don't control.
  • Run unit tests in dev/CI only. They test code, not data.
