☁️ dbt Cloud → dbt platform

What you get on top of dbt Core

dbt Cloud was renamed the dbt platform in 2025. It runs the same dbt engine you use (1.8.6 today) and adds everything around it: a browser IDE, a scheduler, CI that understands dbt, lineage and catalog, cross-project refs, a Semantic Layer API, and smart rebuilds. This page goes through the top features, each with a concrete example and what it would take to do the same with Core alone.

1 · Core vs platform: the map

The key idea

Your SQL, YAML and macros are the same project in Core and on the platform. The platform doesn't change how dbt transforms data. It replaces the glue you would otherwise build yourself: cron/Airflow jobs, CI scripts, manifest storage, schema cleanup, a docs server, a metrics API. Features marked Enterprise need the Enterprise or Enterprise+ plan. Others exist on all or most paid plans (check the pricing page).

2 · No more pip upgrades: release tracks

dbt Core 1.8.6

You pin and upgrade yourself, and every upgrade is a project:

pip install "dbt-core==1.8.6" "dbt-snowflake==1.8.4"
# later: read the changelogs for 1.9, 1.10, 1.11, 1.12, fix the
# deprecations, upgrade the CI image, the Airflow image, every laptop…
dbt Core 1.12

The same, one version later. The 1.9–1.12 features on this site (microbatch, hard_deletes, --sample…) only arrive when you upgrade.

pip install "dbt-core~=1.12.0" "dbt-snowflake~=1.12.0"
dbt platform

Each environment follows a release track and is upgraded automatically:

TrackCadenceFor
v1 Latestcontinuousv1 features, often before OSS
v1 Compatiblemonthlyaligned with the latest OSS 1.x + adapters
v1 Extendedmonthly, 1 behindEnterprise: prod stability
v2 Stable (default for new projects)weeklydbt v2 / Fusion engine

Projects still on 1.3–1.7 must migrate by January 31, 2027. Packages are not auto-upgraded: pin them and commit package-lock.yml.

3 · CI that understands dbt

Follow one pull request from opening to cleanup. For each step, compare what the platform does for you with what you would script with Core.

The Core equivalent (1.8.6)
.github/workflows/dbt-ci.yml (abridged)
on: pull_request
jobs:
  ci:
    steps:
      - run: pip install dbt-snowflake==1.8.*
      - run: aws s3 cp s3://dbt-artifacts/prod/manifest.json prod/   # you store it
      - run: dbt build -s state:modified+ --defer --state prod/ --target ci

The Core equivalent (1.12)

dbt build -s state:modified+ --defer --state prod/ --sample="3 days"
# env vars renamed DBT_ENGINE_* (1.11)

Core 1.12 gives you better building blocks (--empty, --sample). You still own the plumbing.

4 · Compare changes (Advanced CI) Enterprise

Tests tell you whether the code is valid. Compare changes tells the reviewer what the PR does to the data versus production. Pick a change:

PR change
diff
comment posted on the pull request

Works on Snowflake, BigQuery, Databricks, Redshift and Postgres when CI and prod share the same connection. With event_time configured, only the time range present in both is compared, so a CI run on 3 days of data doesn't report every older row as "removed". With Core: audit_helper.compare_relations in a hand-written step.

5 · dbt State: build only what changed Enterprise

Formerly "state-aware orchestration". The job keeps a model-level state and skips a model when neither its code nor its upstream data changed. A freshness/lag setting can also make a model wait a minimum interval before rebuilding again. Here's an hourly job, run with Core and with dbt State:

Run with
● new data landedmodel built· skipped (reused)
Closest with Core 1.8.6 
dbt source freshness
dbt build -s "source_status:fresher+" --state last-run/

This skips the branches whose sources didn't get data (see the Freshness page). It doesn't track code changes per model, wait intervals, or reuse across concurrent jobs.

Closest with Core 1.12

Same source_status:fresher+ pattern. Microbatch (1.9+) also limits each run to recent batches. The model-level skip-and-reuse logic remains a platform feature.

6 · Mesh: ref() across projects Enterprise

Split a monolith into domain projects owned by different teams. The upstream team publishes public, contracted models. Downstream projects reference them without installing the upstream code.

upstream project: finance
models/marts/_marts.yml
groups:
  - name: finance
    owner: {name: Finance data team, email: fin-data@acme.com}
models:
  - name: fct_revenue
    config:
      group: finance
      access: public            # private | protected | public
      contract: {enforced: true}
    latest_version: 2
    versions: [{v: 1}, {v: 2}]
    columns:
      - name: revenue_id
        data_type: int
        constraints: [{type: not_null}]

Groups, access, contracts and versions all work in dbt Core 1.8.6 and 1.12.

downstream project: marketing
dependencies.yml
projects:
  - name: finance
models/roi.sql
select c.campaign_id, sum(r.revenue) as revenue
from {{ ref('campaigns') }} c
join {{ ref('finance', 'fct_revenue', v=2) }} r using (order_id)
group by 1

The two-argument ref is resolved by the platform from finance's latest production run. Catalog draws the lineage across both projects. With Core only, you'd install finance as a package (git dependency), which means you compile and run its code too, or you'd declare its tables as sources.

7 · Semantic Layer: define metrics once, query them anywhere

Metrics live in YAML next to the models (MetricFlow). The platform exposes them through APIs (JDBC, GraphQL) and integrations (Google Sheets, Tableau, Power BI, Hex…), so "revenue" means the same thing in every tool. With Core, you can define and validate them and query locally with mf query, but there is no shared API.

1.8.6: legacy spec 
semantic_models:
  - name: orders
    model: ref('fct_orders')
    defaults: {agg_time_dimension: ordered_at}
    entities:
      - {name: order, type: primary, expr: order_id}
      - {name: customer, type: foreign, expr: customer_id}
    dimensions:
      - name: ordered_at
        type: time
        type_params: {time_granularity: day}
      - {name: status, type: categorical}
    measures:
      - {name: revenue, agg: sum, expr: amount}
metrics:
  - name: revenue
    label: Revenue
    type: simple
    type_params: {measure: revenue}
1.12: latest spec 
models:
  - name: fct_orders
    semantic_model: {enabled: true}
    agg_time_dimension: ordered_at
    columns:
      - name: order_id
        entity: {type: primary, name: order}
      - name: customer_id
        entity: {type: foreign, name: customer}
      - name: ordered_at
        granularity: day
        dimension: {type: time}
      - name: status
        dimension: {type: categorical}
    metrics:
      - name: revenue
        type: simple
        agg: sum
        expr: amount

Migrate with dbt-autofix deprecations --semantic-layer. The latest spec doesn't support cross-project refs yet.

# the same question from anywhere (platform CLI / IDE / API):
dbt sl query --metrics revenue --group-by metric_time__month,customer__country
# → the platform generates the SQL (joins through entities) and runs it on your warehouse

8 · Catalog, IDE, Copilot and the rest

🗺️ Catalog

Lineage across all projects, down to column level. Shows model health (last run, tests, freshness), run times and usage.
Core: dbt docs generate && dbt docs serve, a static site with model-level lineage that you host.

💻 Studio IDE & Canvas

Browser IDE with git, autocomplete, compiled SQL preview, DAG and automatic deferral, so analysts need no local Python setup. Canvas builds models visually (drag-and-drop) and produces real SQL.
Core: your editor + a venv + profiles.yml per person.

🤖 Copilot

Generates documentation, data tests, semantic models and SQL from natural language, inside the IDE and Canvas.
Example: "add tests for fct_orders" adds unique/not_null on the key and relationships on the FKs.

⏰ Scheduler & orchestration

Jobs per environment with cron, job chaining (run when another job completes), API/webhook triggers, Slack/email notifications, and run history with model timing.
Core: Airflow/Dagster/cron + your own alerting.

📊 Auto-exposures

Tableau / Power BI dashboards appear in the lineage automatically, and the job can refresh their extracts right after the models they use are rebuilt.
Core: hand-written exposures: YAML that drifts.

🔌 Discovery API & Insights

GraphQL API over the metadata (models, runs, tests, lineage) for your own tooling. Insights is a query and exploration tool built on the project's context.
Core: parse manifest.json / run_results.json yourself.

🔐 Security & admin

SSO, role-based access, audit logs, managed credentials per environment, SOC 2 hosting, IP restrictions.
Core: whatever your runner and secrets manager provide.

⚡ dbt v2 / Fusion

The default track for new platform projects is dbt v2, a new Rust engine with SQL understanding (static analysis, faster parsing, native lint). It also exists outside the platform (local CLI, VS Code extension). Core 1.12 lets you try its parser with --use-v2-parser.
